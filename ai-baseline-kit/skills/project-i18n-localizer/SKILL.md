# 项目国际化处理

## 目标
按照当前项目的真实规则处理用户可见文案和国际化。该 skill 可以在用户明确要求 i18n 时独立使用，也可以作为 `baseline-structure-skill` 或 `baseline-conformance-skill` 发现国际化问题后的专项跟进。

整包植入模式下：
- 优先读取 `ai-baseline-kit/AGENTS.md`、`ai-baseline-kit/docs/baseline-rules.yml` 和 `.ai-frontend-assembler/project-scheme.yml`。
- 扫描和修改对象是 `ai-baseline-kit/` 的父目录，也就是业务项目根目录。
- 除非用户明确要求维护规范包，不修改 `ai-baseline-kit/` 内文件。

## 规则作用范围
在处理国际化前，先判断项目采用哪种基线接入模式。不得因为新增基线包而默认重写存量项目。

### 新项目
新项目是指项目初始化时就采用本基线，或经项目地图明确标记为新项目。新项目的国际化规则全局生效：

- 所有语言资源的翻译 map 统一使用扁平对象。
- 所有模块使用领域化点号 key。
- 项目内不得混用树形翻译对象和扁平翻译对象。
- 新增模块、共享文案和后续维护都必须遵守同一套格式。

### 旧项目植入
旧项目是指已经存在业务代码、项目结构或 i18n 体系，之后才植入本基线。旧项目采用“存量冻结、增量遵守”的策略：

- 不修改植入前已有的语言资源、key 结构、i18n 初始化、解析配置或项目目录结构。
- 不因为旧项目中存在树形资源，就发起全量树形转扁平迁移。
- 后续新增模块必须使用扁平语言资源对象和领域化点号 key。
- 新模块优先将 locales 放在模块自身目录，并通过项目已有的装配方式接入；不要为了接入新模块重写旧的集中式资源。
- 如果修改旧模块，默认沿用该模块原有的资源格式和调用约定；只有用户明确要求迁移时，才规划独立的迁移任务。
- 旧项目可以在“冻结的历史模块”和“按新基线开发的新模块”之间暂时存在两种物理结构。这是存量兼容边界，不属于本 skill 的违规；但同一个新模块内部不得混用两种结构。
- 如果旧项目的现有集中式 i18n 机制无法在不改动存量资源的前提下接入扁平新模块，应报告兼容性边界，优先采用模块级资源或项目已有扩展点，不得静默修改旧资源。

判断不明确时，优先依据 `project-scheme.yml`、项目根入口规则、已有目录和提交前的 i18n 现状；无法安全判断时，在方案中标记为 `legacy_or_new: unknown`，不要擅自做全量改造。

## 必须先发现
在规划或修改国际化内容前，按顺序检查：

1. `ai-baseline-kit/AGENTS.md` 或项目根 `AGENTS.md`
2. `ai-baseline-kit/docs/baseline-rules.yml` 或同等项目规则
3. `.ai-frontend-assembler/project-scheme.yml` 或同等项目地图
4. 包管理清单和框架入口
5. 现有 i18n 初始化、语言资源、语言切换器、provider、`t()` 或翻译 API 用法
6. 附近功能、页面或模块文件，用于推断领域命名和资源归属
7. 判断本次变更属于全局新项目规则，还是旧项目的新增模块范围

不要向用户询问可以从这些文件中发现的事实。

## 扁平资源格式
在本 skill 的生效范围内，统一采用：**扁平语言资源对象 + 领域化点号 key**。

```ts
export const zhCN = {
  'deviceAccess.title': '设备接入',
  'deviceAccess.stats.gisRate': 'GIS 率',
  'deviceAccess.action.refresh': '刷新'
}
```

规则如下：

- 翻译 map 必须是扁平对象；翻译 key 直接作为对象的一级属性，值为文案或当前 i18n 库要求的叶子值。
- `locale`、`namespace` 等库要求的外层包装可以保留，但包装内部的翻译 map 必须扁平。
- key 使用点号表达模块、领域和语义层级，例如 `deviceAccess.stats.gisRate`；点号是 key 命名的一部分，不代表资源对象必须嵌套。
- 调用方式保持项目原生 API，例如 `t('deviceAccess.stats.gisRate')`；如果当前库默认把点号解释为嵌套路径，必须配置或使用该库等价的字面 key 解析方式。
- 新项目全局遵守扁平格式；旧项目只要求本次新增模块及其新增资源遵守扁平格式，不要求回溯修改旧资源。
- 在生效范围内，所有语言资源使用完全相同的 key 集合。
- 不允许把同一个 key 同时作为叶子值和其他 key 的前缀，例如同时存在 `deviceAccess.stats` 和 `deviceAccess.stats.gisRate`。

只有用户明确要求对旧项目做国际化迁移时，才执行树形转扁平。迁移任务必须单独声明范围、影响面和回滚方式；普通新增模块任务不得借机改造旧资源。

## 必须先发现后的决策流程
每次任务都按以下流程执行：

1. **识别**：判断项目是新项目还是旧项目植入，判断是否已有 i18n、使用什么库、资源放在哪里、key 如何命名、插值如何写、组件如何调用翻译。
2. **确定范围**：
   - 新项目：按全项目范围执行扁平资源规则。
   - 旧项目：冻结存量，只对新增模块及本次新增资源执行扁平资源规则。
   - 修改旧模块：默认遵循旧模块现有格式，不主动混入新格式或触发迁移。
3. **决策**：
   - 如果项目规则要求国际化，将国际化视为必做项。
   - 如果项目已经有 i18n，只保留其库、provider、语言列表、插值语法和调用 API；在本次生效范围内使用扁平资源 map。
   - 如果规则和现有代码都没有要求 i18n，不要默认强行引入；除非用户明确要求新增国际化。
4. **配置**：当生效范围要求 i18n 但当前缺失时，采用最小的项目原生方案：依赖、初始化文件、扁平资源文件、provider 接入、默认语言和调用约定。
5. **抽取**：把用户可见文案移入语言资源。新增 key 前先复用语义和语气都匹配的现有 key；旧项目不得为了复用旧 key 而重写存量资源。
6. **翻译**：翻译要简洁、自然，适合 UI 空间和未来出海使用。
7. **验证**：按项目模式验证：新项目检查全局一致性；旧项目只检查本次新增模块和变更文件，不把历史资源格式作为新增违规。

抽取或翻译文案时，读取 `references/i18n-patterns.md` 获取命名、文案、扁平资源和插值规则。

## 独立使用规则
- 新项目：保留项目选定的 i18n 库、provider、语言列表、插值语法和调用 API；所有语言资源使用扁平对象。
- 旧项目：保留既有 i18n 库、provider、语言列表、插值语法、调用 API 和存量资源格式；新增模块的语言资源使用扁平对象，不迁移旧模块。
- 项目要求但缺少 i18n：只补当前生效范围内项目可运行所需的最小体系，资源 map 使用扁平对象。不要引入远程翻译平台、运行时语言资源加载或大范围重写，除非项目已有这种模式。
- 没有 i18n 要求：说明当前项目看起来不要求国际化，默认不新增体系。用户明确要求新增 i18n 时，再继续做最小适配。

## 项目形态默认值
只有在发现阶段确认项目符合对应形态时，才使用这些默认值：

- React 项目使用 `i18next` 和 `react-i18next`：使用 `useTranslation()` 和 `t("domain.key", params)`；新项目全局或旧项目新增模块的翻译 map 使用扁平 key，并按项目配置正确解析点号 key。
- 扁平 TypeScript 资源对象：每个生效范围内的语言文件增加相同 key，禁止新增嵌套翻译对象。
- i18next 插值：使用 `{{name}}`、`{{count}}`、`{{seconds}}` 等。
- Huawei 3800 前端形态：资源位于 `src/i18n/resources/zh-CN.ts` 和 `src/i18n/resources/en-US.ts`，使用扁平对象和 `systemConfig.action.save` 这类领域命名。

## 与基线 skill 协作
- 被 `baseline-structure-skill` 调用时，消费已规划的模块、页面、API、样式范围，并补充国际化部分：项目模式、适用范围、扁平资源文件位置、key 领域、动态占位符、解析配置和验证方式。
- 被 `baseline-conformance-skill` 调用时，只修复或报告本次生效范围内的国际化违规：新增模块资源未扁平化、缺少语言条目、未抽取可见文案、key 领域错误、key 前缀冲突、动态文案硬编码拼接、语言资源未成对；旧项目的历史树形资源不作为新增违规。
- 基线 skill 负责结构和边界；本 skill 负责 i18n 决策、适用范围、扁平资源格式和文案质量。

## 输出要求
规划时包含：
- `legacy_or_new` 判断及依据
- 国际化规则的生效范围
- 是否必须国际化
- 需要触碰的文件或资源位置
- 扁平资源格式和 key 命名策略
- i18n 库的点号 key 解析配置
- 动态占位符策略
- 验证命令或检查点

实施时保持改动聚焦，不改变无关项目行为。
