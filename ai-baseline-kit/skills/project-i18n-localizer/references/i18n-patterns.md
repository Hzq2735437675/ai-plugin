# i18n 规则模式

## 规则生效范围
先区分项目模式，再应用资源规则：

- **新项目**：本规则全局生效。所有语言资源统一使用扁平对象和领域化点号 key，项目内不得混用树形翻译对象和扁平翻译对象。
- **旧项目植入基线**：存量资源和旧模块保持不变；只有后续新增模块及其新增资源使用扁平对象和领域化点号 key。旧模块历史格式不作为新增违规，也不要求在普通功能开发中迁移。
- **旧模块增量修改**：默认沿用该模块现有资源格式和调用约定，不在一个旧模块内部混入新的物理结构；迁移必须由用户单独授权。

旧项目可能暂时存在“历史模块使用旧格式、新模块使用扁平格式”的边界状态。不要为了消除这种历史并存而修改存量项目。

## 资源结构与 Key 命名
在规则生效范围内，语言资源统一使用扁平对象：翻译 key 直接作为翻译 map 的一级属性，值为文案或当前 i18n 库要求的叶子值。

```ts
export const zhCN = {
  'deviceAccess.title': '设备接入',
  'deviceAccess.stats.gisRate': 'GIS 率',
  'deviceAccess.action.refresh': '刷新'
}
```

- 允许保留 `locale`、`namespace` 等 i18n 库要求的外层包装，但包装内部的翻译 map 仍必须扁平。
- 逻辑 key 使用点号分隔的领域命名，例如 `login.title`、`userManagement.form.username`、`systemConfig.message.saveFailed`、`deviceAccess.stats.gisRate`。
- 点号属于完整 key 的命名，不要求资源对象按点号嵌套；调用仍使用项目原生 API，例如 `t('deviceAccess.stats.gisRate')`。
- 如果当前 i18n 库默认将点号解释为嵌套路径，配置等价的字面 key 解析方式；不要通过改动旧项目资源来规避解析问题。
- 只有真正共享的动作或标签才使用 `common.*`，例如 `common.search`、`common.cancel`。
- 避免创建含义几乎相同的重复 key。上下文和语气一致时复用现有 key。
- key 要表达语义，不要照抄文案。优先 `action.save`，不要用 `buttonSaveText`。
- 在新项目或新增模块范围内，不允许同时存在叶子 key 和其子 key，例如 `deviceAccess.stats` 与 `deviceAccess.stats.gisRate`。

只有用户明确要求旧项目国际化迁移时，才执行树形资源转扁平资源。迁移前必须明确范围、影响面、解析配置和回滚方式；普通新增模块任务不得修改旧树形资源。

## 可见文案抽取
- 抽取所有用户可见的标签、按钮、占位符、空状态、页面标题、表头、菜单名、校验提示、toast、弹窗标题、确认文案和 tooltip。
- 不抽取技术常量、API 值、路由路径、权限 ID、CSS 类名、枚举 key、只给开发者看的日志或测试选择器，除非它们会展示给用户。
- 把完整句子放进语言资源，不要在代码中拼接翻译片段。
- 不要把翻译文案和动态数据直接字符串拼接；不同语言的语序可能不同。

## 动态插值
- 使用当前库的插值语法。i18next 使用 `{{name}}`。
- 同一个 key 在所有语言中必须使用相同占位符名称。
- 优先使用完整模板：
  - 推荐：`Delete user "{{username}}"?`
  - 避免：`Delete ` + username + `?`
- 占位符名称要清晰，例如 `{{count}}`、`{{name}}`、`{{username}}`、`{{seconds}}`、`{{total}}`。
- 数量和单位优先保持完整短语可翻译，除非项目已经稳定采用独立单位 key。

## 中文文案
- 中文 UI 文案要短、准、清楚。
- 使用项目中已经出现的产品词和领域词。
- 密集型运营界面避免过度正式或解释型文案。
- 占位符保持可操作，例如 `请输入用户名`、`搜索设备 / 通道`。

## 出海英文文案
- 英文要自然，不做逐字硬译。
- 标签尽量紧凑，例如 `Device List`、`Role Name`、`Save`、`Reset`。
- 描述和消息使用简洁句式。
- 失败消息要清楚，例如 `Failed to save configuration`。
- 除非是必须保留的协议或产品术语，避免中国本地缩写；例如 `GB/T28181` 应保持原样。
- 品牌名、协议名、型号和标准名按项目既有写法保留，除非项目已经有官方译法。

## 验证清单
- 已识别项目是新项目还是旧项目植入，并记录规则生效范围。
- 新项目的所有语言资源翻译 map 都是扁平对象，没有业务层级嵌套翻译对象。
- 旧项目只检查本次新增模块和变更文件；历史语言资源和旧模块格式不作为新增违规。
- 每个新增用户可见文案都有语言 key。
- 生效范围内每个新增 key 都存在于所有必需语言资源中，语言 key 集合一致。
- 新项目或新增模块范围内不存在叶子 key 与其子 key 的前缀冲突。
- 当前 i18n 库能按完整点号 key 正确解析新增扁平资源。
- 同一个 key 的所有语言使用相同插值变量。
- 没有把可翻译句子拆成依赖语序的片段。
- 新 key 的领域归属和功能或模块所有权一致。
- UI 文案足够短，适合按钮、菜单、表头和紧凑面板。
